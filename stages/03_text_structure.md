# Стадия 3 — Text structure

**Цель.** Orchestrator понимает, что в этом корпусе — «единица
перевода» (то, что переводится одним вызовом translator-агента) и
«единица батча» (то, что коммитится одним заходом на GitHub Pages).
Артефакт — `$HEB_ROOT/articles_catalog.json`.

Перед этой стадией обязательно прочитай
[`reference/source_loader/CATALOG_STRUCTURE.md`](../reference/source_loader/CATALOG_STRUCTURE.md) —
там разобрана трёхуровневая иерархия (Chapter → Article → Chunk) и
что значит каждое поле.

## 3.1 Базовая иерархия

`zohar-translator` ожидает плоский список **статей** в
`articles_catalog.json`. Каждая статья принадлежит **главе** (для
группировки на сайте и в коммитах). Длинная статья режется
orchestrator'ом на **чанки** во время перевода (по `CHUNK_BUDGET_CHARS`,
default 7500) — это техническая деталь, тебе её настраивать не нужно.

Тебе нужно решить с оператором:

- что считается «статьёй» (одна единица перевода);
- что считается «главой» (группировка статей).

## 3.2 Развилка по корпусу

**(Q 1 из 3: что в твоём корпусе — естественная «статья»?)**

Объясни варианты на примерах:

- **Зоар:** статья ≈ один комментарий «Перуш ха-Сулам» на отрывок
  (примерно 1000–5000 символов).
- **Танах:** статья = глава книги (Бытие 1, Бытие 2, …).
- **Талмуд:** статья = один лист (`Daf 2a`, `Daf 2b`, …).
- **Современная книга:** статья = глава или подраздел (если глава
  слишком длинная — например > 50k символов — лучше дробить).

Принцип: статья должна влезать в один контекст translator-агента
(практически — до ~30k символов оригинала; всё что больше — режется
на чанки автоматически, но качество страдает; лучше сразу делить
крупнее на уровне статьи).

**(Q 2 из 3: что — «глава»?)** Группировка статей. На сайте каждой
главе — своя страница с оглавлением статей внутри. В git-коммите
закрытие главы триггерит rebuild сайта. Слишком мелкая глава →
много шума в коммитах. Слишком крупная → редкие апдейты сайта.
Ориентир: 5–30 статей на главу.

**(Q 3 из 3: сколько статей всего?)** Если знаешь из стадии 2 —
напомни цифру. Если глав много (> 100) — переведи, что прогон займёт
дни-недели реального времени; это нормально, orchestrator переживает
лимиты.

## 3.3 Сборка `articles_catalog.json`

Если шёл по Sefaria fast-path (стадия 2a) — `Source/catalog.json`
уже содержит иерархию глав/статей. Тебе нужен скрипт, который
пробежится по нему и выдаст плоский `articles_catalog.json`.
Образец — в коде `download_sefaria.py` (там в конце есть генерация
catalog'а). Если шаблон корпуса совпадает — переиспользуй; иначе
напиши маленький конвертер (10-50 строк), читающий `Source/catalog.json`
и пишущий `articles_catalog.json`.

Если шёл по своему loader'у (стадия 2b/c) — формат
`articles_catalog.json` уже описан в `CATALOG_STRUCTURE.md`. Собери
вручную или допиши свой loader, чтобы он сразу его генерил.

Минимальная схема каждой записи:

```json
{
  "article_id": "Zohar.Bereshit.1",
  "chapter_id": "Bereshit",
  "title_he": "...",
  "title_ru": "...",
  "char_count": 4823,
  "source_path": "Source/Zohar_he.json#/Bereshit/1"
}
```

Точные поля — в `CATALOG_STRUCTURE.md`.

## 3.4 Проверка

Загляни в `articles_catalog.json`. Проверь:

- Количество записей ≈ ожидаемое (сравни с тем, что сказал оператор
  в Q 3).
- Поле `char_count` заполнено (нужно orchestrator'у для оценки чанков).
- Все `chapter_id` встречаются хотя бы в одной статье; нет «осиротевших».
- Сортировка имеет смысл (например, по канон. порядку Танаха, а не
  алфавитная — иначе сайт будет нечитаем).

## 3.5 CHUNK_BUDGET_CHARS

Если в корпусе много статей > 10k символов — увеличь
`CHUNK_BUDGET_CHARS` в `project.config` (default 7500 рассчитан под
Зоар). Ориентир: ≈⅓ от 95-го перцентиля длины статьи. Слишком малое →
лишние чанки → медленнее. Слишком большое → translator-агент может
не уложиться в свой контекст.

## 3.6 Запись прогресса

```json
{
  "current_stage": 4,
  "completed_stages": [1, 2, 3],
  "answers": {
    ...,
    "stage3.article_unit": "сeфария-секция",
    "stage3.chapter_unit": "книга-параша",
    "stage3.articles_total": 1287,
    "stage3.chapters_total": 54,
    "stage3.chunk_budget_chars": 7500
  }
}
```

## Чек-лист стадии 3

      содержит ожидаемое число записей.
- [ ] `CHUNK_BUDGET_CHARS` подобран под длину статей.
- [ ] Объём корпуса понятен (число статей × средняя длина) — оператор
      примерно представляет порядок времени перевода.
