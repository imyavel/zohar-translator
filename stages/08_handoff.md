## 8.2 Telegram-бот (опционально, но рекомендую)

Полный прогон корпуса — часы или дни. Оператор не будет сидеть у
экрана. TG-бот шлёт статус: «перевожу X из Y», «упёрся в лимит,
жду до HH:MM», «глава Z готова, deploy успешен», «ошибка».

Если ещё не настроен:

- **(Q 1 из 2: настраиваем Telegram-бот сейчас?)** «Да» / «Пропустить».
- Если «да»:
  1. Открой Telegram → найди `@BotFather` → `/newbot` → имя → username.
     Получишь токен формата `1234567890:ABC...`.
  2. **Никогда не выводи токен в чат.** Прими через input, запиши
     в `.env` как `TG_BOT_TOKEN=...`.
  3. Найди в Telegram свежесозданного бота, напиши ему `/start`.
  4. **(Q 2 из 2: chat_id для уведомлений?)** Открой
     `https://api.telegram.org/bot<TOKEN>/getUpdates` в браузере, в
     ответе найди `chat.id` от своего user'а (положительное число) —
     это и есть `TG_PRIVATE_CHAT_ID`. Запиши в `.env`.

Проверка: `python src/main.py` — бот должен прислать в чат
приветственное сообщение и начать слать heartbeats.

## 8.3 Способы запуска

Три варианта, все из корня репо:

```bash
# 1. GUI (tkinter) — для оператора-человека
python src/gui.pyw

# 2. Orchestrator + Telegram, headless
python src/main.py

# 3. Orchestrator headless без Telegram
python src/main.py --no-bot
```

Покажи оператору все три, объясни когда какой.

## 8.4 Что мониторить во время прогона

Покажи оператору, что наблюдать (либо через GUI, либо через TG):

- **Текущий батч / прогресс.** Сколько глав закрыто, сколько
  осталось, оценка времени до конца.
- **Лимиты.** Когда orchestrator упирается в 5-часовое окно — он
  напишет «жду до HH:MM», это норма, не паника.
- **Weekly limit.** Раз в 7 дней может упереться в недельный лимит —
  тогда ждёт до конкретной ISO-даты. Тоже норма.
- **Deploy.** Каждая закрытая глава → коммит в GH-репо → видно на
  GH-странице. Если 3 коммита подряд не видно — что-то с токеном
  (истёк, нет прав), смотреть логи.
- **Ошибки.** В TG приходят теги `[ERROR]` — это требует внимания.
  Простые (network blip) orchestrator переживает сам; persistent —
  останавливают батч, нужно ручное вмешательство.

## 8.5 Что делать если упал процесс

Pipeline переживает перезапуск:

- Killed orchestrator (питание / ребут / случайный Ctrl-C) →
  `python src/main.py` снова, resume через `partial_state.py`
  автоматический. Незавершённый батч добежит, дальше как обычно.
- Поломанный коммит на GH (rejected, конфликт) → reset через
  `corpus_tools/wake_recover.py`, потом снова `python src/main.py`.
- Зависший batch (translator подвис, не отвечает) →
  `corpus_tools/kill_stale_batch.py`, потом restart.

Все три скрипта документированы в [`ARCHITECTURE.md`](../ARCHITECTURE.md).
Не запоминай их наизусть оператору — он откроет ARCHITECTURE.md, когда
понадобится.

## 8.7 Что сказать оператору на прощание

Кратко (1-2 предложения):

> «Система готова. Запускай `python src/gui.pyw`, нажимай **Старт**.
> Прогон корпуса займёт примерно <оценка> — следи через Telegram-бота;
> если что — открой ARCHITECTURE.md, там описаны все рантайм-сценарии.»

Если знаешь — дай конкретную оценку времени (число статей × средний
размер чанка × ~30 секунд на чанк / параллельность). Если не знаешь —
скажи «уточним после первого часа прогона по фактической скорости».
